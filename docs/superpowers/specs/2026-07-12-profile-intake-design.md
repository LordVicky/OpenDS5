# Profile intake: contributions land in the public profiles repo

Date: 2026-07-12
Status: approved (design)

## Problem

Adding a game profile to the library is manual. A profile is exported from the app, hand-copied
into `profiles/library/` in the private app repo, `build-index.mjs` is run by hand, and
`publish-library.mjs` pushes the result to the public mirror. Nobody but the maintainer can
contribute, and every step is a chance to forget one.

## Approach

The mirror exists only because the app repo is private and `raw.githubusercontent.com` will not
serve a private repo anonymously. If contributions are public anyway, the contribution repo *is*
the repo the app reads. So there is one public repo, not two, and no publish step.

`OpenDS5-Profiles` becomes the source of truth **and** what the app fetches. `LIBRARY_INDEX_URL`
already points at it, so the app does not change.

### Why not keep the mirror

`publish-library.mjs` replaces the mirror's `profiles/library/` wholesale (`rmSync` then `cpSync`)
so that deletions propagate. Under a two-repo scheme where contributors merge into the mirror, the
first publish would **silently delete every merged community profile**. Retiring the mirror removes
that hazard rather than papering over it.

## Repository layout

### `OpenDS5-Profiles` (public)

```
profiles/library/<game-slug>.json   contributors add these
profiles/library/index.json         generated by CI; never hand-edited
profiles/library/native.json        curated by the maintainer
validator/                          vendored from the app; see "Validator drift"
scripts/build-index.mjs
scripts/validate-profile.mts
package.json                        tsx devDependency
.github/workflows/validate.yml      on PR: validate every profile
.github/workflows/index.yml         on push to main: regenerate index.json and commit
.github/pull_request_template.md
README.md                           contributor guide
```

### `OpenDS5` (private, later public)

Keeps only the app. `profiles/library/`, `build-index.mjs`, `validate-profile.mts`,
`publish-library.mjs`, and `library-check.yml` move out. It gains `scripts/sync-validator.mjs`.

## Contributor flow

1. Export a profile from the app: Trigger Profiles → Export.
2. Fork `OpenDS5-Profiles`, add `profiles/library/<game-slug>.json`.
3. Fill in `meta.game`, `meta.author`, `meta.description`. **Leave `meta.tier` out.**
4. Open a PR. CI validates the profile with the real shared validator — the same rules the app
   enforces at install time, so a profile that would fail on install fails in CI instead.
5. The maintainer hardware-tests it. If it passes, they set `"tier": "verified"` and merge.
   Otherwise it merges as-is and stays `community`.
6. On merge to `main`, CI regenerates `index.json` and commits it.
7. The app picks the profile up on its next library fetch. No app release is needed.

### Contributors never edit `index.json`

It is generated. A hand-edited index would conflict on every concurrent PR and could claim
capabilities the profile does not have. CI owns the file; the PR template says so, and the
validate workflow fails a PR that modifies it.

### Tiers

`tier` is absent on a contribution, and an absent tier already coerces to `community` in the app —
an unlabelled profile never presents itself as maintainer-verified. `verified` means the maintainer
hardware-tested it, and only the maintainer sets it, at merge time.

## Validator drift

The validator and `describeCapabilities` are vendored into the public repo so its CI can run the
real rules. That means two copies of the schema, which can drift.

`scripts/sync-validator.mjs` in the app repo:

- copies `trigger-profiles.ts`, `profile-capabilities.ts`, and `protocol.ts` into a clone of
  `OpenDS5-Profiles` under `validator/` and pushes (run from the maintainer's machine with their
  own git credentials — no cross-repo token, exactly as `publish-library.mjs` did),
- `--check` compares the published copies against the app's and exits non-zero if they differ.

App CI runs `--check`, so the app's schema and the CI gating contributions cannot silently diverge.
The three files are copied verbatim rather than hand-extracted, so the check is an exact
comparison. `trigger-profiles.ts` and `profile-capabilities.ts` import only *types* from
`protocol.ts`, so no runtime code beyond these three files is pulled in.

## Workflows

**`validate.yml`** — on pull request touching `profiles/**`:
- `node scripts/build-index.mjs --check-profiles` validates every profile through the vendored
  validator and fails with the validator's own message.
- fails if the PR modifies `profiles/library/index.json`.

**`index.yml`** — on push to `main` touching `profiles/**`:
- `node scripts/build-index.mjs` regenerates `index.json` (capabilities, tier, origin) and commits
  it back to `main` if it changed. Idempotent: a no-op push does not commit.

`native.json` is not a profile and is excluded from the profile scan, as it already is in
`build-index.mjs`.

## Error handling

- An invalid profile fails the PR with the validator's message (`meta.tier must be 'verified' or
  'community'`, `triggers.l2.base.zones must be 10 integers 0-100`, …).
- A profile whose file name is not a safe slug is rejected: the name is interpolated into the
  library URL the app fetches.
- The index rebuild on `main` cannot fail a merge — if regeneration errors, the workflow fails
  loudly and `index.json` keeps its previous, valid contents. The app keeps serving the old index
  rather than a broken one.

## Testing

- `build-index.mjs --check` in the public repo's CI is the gate: it validates every profile and
  asserts the index is in sync.
- A fixture PR with a deliberately invalid profile confirms CI rejects it (done once, by hand).
- `sync-validator.mjs --check` in the app's CI proves the vendored copy matches.

## Out of scope

- Automated tier promotion. Verification is a human hardware test.
- Contributions to `native.json` (maintainer-curated).
- Moving the profile library back into the app repo when it goes public. Profiles stay separate:
  contributors do not need the app, profile merges do not touch app code, and profile updates do
  not wait on an app release.
